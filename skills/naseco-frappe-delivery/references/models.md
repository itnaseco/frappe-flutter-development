# Process, decision and architecture models

- Use Mermaid for explanatory views. Split material documentation by purpose: system context, DocType relationships, document lifecycle, API sequence, offline sync or migration. Use a separate diagram when the audience or question changes. Cite source components or OpenSpec requirements and label current, proposed or partial behavior. Render-check when supported.
- Use editable .bpmn files for formal multi-role processes, cross-system handoffs, parallel work, timeouts or escalation. Split capability maps, end-to-end processes and subprocesses. Show ownership, start/end events, exceptions and meaningful gateway conditions. Use sequence flows within a participant and message flows between participants.
- Use editable .dmn files for material decision rules. Specify typed inputs, outputs, hit policy, missing-input and no-match handling, owner and version. Test boundaries, overlapping rules and representative cases. Link the calling BPMN task or Frappe service. Identify the authoritative implementation and test parity when the model documents existing code.
- Distinguish descriptive models from executable ones. For executable models use the approved engine and supported versions, verify model import and schema/lint results, and test routing, decisions, retries and failure paths on that runtime. Map task IDs to code and record who owns incidents and in-flight version changes. Frappe retains document permissions and transaction authority. Camunda BPMN, DMN, FEEL and process-test skills are optional adapters for approved Camunda work.
